## Does Zotero have an API or CLI?

### API (official)
- **Zotero Web API** (official): create/read/update items, collections, attachments, tags, etc.
  - Docs: https://www.zotero.org/support/dev/web_api/v3/start
  - Auth: API key with library access.
  - Best for: syncing your automation to a **Zotero cloud library** (personal or group).

### CLI (official / not really)
- Zotero does **not** ship an official full-featured CLI for library management.
- But you can automate via:
  - Web API clients (Python/R/Node) from the command line
  - Local SQLite access (possible but fragile; not recommended for automation unless you fully control the environment and accept breakage risk)
  - Better BibTeX + exports (not a general API, but very useful in doc workflows)

## Third-party tools commonly used
- **Zotero Better BibTeX (ZBB)** plugin (very popular): stable BibTeX/CSL-JSON export, citation keys, auto-export.
  - https://retorque.re/zotero-better-bibtex/
- **zotero-cli (community)**: CLI wrapper around the Web API (various projects exist; quality varies). If you choose this, pin a specific tool and version and test on your OS.
- **Python libraries**:
  - `pyzotero` (widely used) to talk to the Web API.
- **R ecosystem**:
  - There are R packages and scripts that can call the Web API (often via `httr2`) and can also help generate bibliographies for Quarto, but most teams still use either Better BibTeX exports or Python for ingestion.

## 4 options to automate your PDF-folder → Zotero workflow (ranked)

### Option 1 (highest confidence): Zotero + “Add PDF” + built-in metadata retrieval + Better BibTeX auto-export
**What it is**
- Put PDFs in a “drop folder”, import them into Zotero (desktop), then use Zotero’s metadata retrieval (when available), and maintain an **auto-exported** `.bib`/CSL JSON via Better BibTeX.

**Pros**
- Lowest engineering effort; leverages Zotero’s best-supported path.
- Plays very well with Quarto/GitHub Pages workflows (exported `.bib` committed).

**Cons / risks**
- Not fully “headless”; relies on desktop app + plugin running locally.
- Metadata retrieval quality varies (scanned PDFs, reports, some publishers).

**Tradeoffs**
- Fast to adopt; less customizable ingestion logic.

### Option 2: Fully scripted ingestion via Zotero Web API + DOI-based metadata (Crossref) + PDF attachments
**What it is**
- A script walks a folder of PDFs, tries to extract DOI, queries Crossref (or other sources), creates a Zotero item via Web API, then uploads/links the PDF as an attachment.

**Pros**
- Fully automatable and repeatable.
- Works well for “team library hygiene” (tags, collections, dedup rules).

**Cons / risks**
- DOI extraction is imperfect.
- Uploading attachments via API has constraints and extra steps; can be slower.
- You must design deduplication rules carefully.

**Tradeoffs**
- Most maintainable “real automation”, but more up-front work.

### Option 3: Use a dedicated reference-extraction tool (GROBID) to parse PDFs → structured metadata → Zotero API
**What it is**
- Run GROBID (service) locally; it extracts bibliographic metadata from PDFs even when no DOI exists; then push results into Zotero.

**Pros**
- Best for reports, book chapters, older/scanned-ish docs where DOI is absent.
- Can outperform DOI-only pipelines for non-journal material.

**Cons / risks**
- Additional infrastructure (Java service).
- Still needs QA; outputs can be wrong and need human review.

**Tradeoffs**
- Higher complexity; highest payoff when PDFs are messy.

### Option 4: Treat Zotero as the “human curation UI”; automation only produces a staging file (RIS/BibTeX/CSL-JSON)
**What it is**
- Script produces a RIS/BibTeX/CSL-JSON file from PDFs; a human imports it to Zotero and fixes anything.

**Pros**
- Simple, low risk to the library.
- Great when correctness matters more than full automation.

**Cons / risks**
- Not fully automated end-to-end.

**Tradeoffs**
- Best if you want guardrails and review gates.

4) Optional: `exports/`

### Step-by-step workflow
1) **Run GROBID locally**
   - Use Docker, pin a version.
2) **Scan & fingerprint PDFs**
   - Recursively find PDFs.
   - Compute a stable fingerprint (SHA256) for provenance and dedup.
3) **Extract metadata with GROBID**
   - Use `grobid-client-python` to call `/processFulltextDocument` or `/processHeaderDocument`.
   - Parse returned TEI/XML into structured fields.
4) **Normalize + enrich**
   - Normalize authors, dates, containers.
   - If DOI detected, optionally query Crossref to improve quality (especially journal metadata).
5) **Create a review queue**
   - Flag items missing: title, year, authors, container, or with low confidence.
   - Flag possible duplicates (same DOI; or fuzzy match title+year).
6) **Curator import into Zotero Desktop (Group Library)**
   - Import RIS/BibTeX/CSL-JSON into Zotero Desktop (exact format depends on what you choose to emit).
   - Curator fixes flagged items using the review queue.
   - Curator attaches PDFs (drag/drop or “Find Available PDF” where applicable).
7) **(Optional) Downstream export for docs**
   - Use Better BibTeX in Zotero to auto-export a `.bib` used by Quarto books (if desired).

### Verification / Definition of Done (for each run)
- [ ] Run completes with an auditable summary (counts, failures).
- [ ] `review_queue.csv` produced and triaged (at least for “critical” items).
- [ ] No uncontrolled duplicate explosion (same DOI appears once in import set; fuzzy duplicates reviewed).

## 3) How metadata extraction improves chunking (concrete improvements)

### A. Better header/footer removal (biggest near-term win)
Today you use: “short repeated lines in many elements” heuristic.

With document metadata you can add stronger rules:
- If bibliographic `title` is known, drop lines that are a near-match to the title (common running header in reports).
- If authors / org / report number known, drop those repeated lines too.
- If OpenAlex/Crossref returns a `container_title` (journal) and year, drop patterns like `Journal Name • 2021` repeated on every page.
- For internal reports: detect “DRAFT”, “FOR OFFICIAL USE ONLY”, “USACE”, district names, project names—then treat these as candidate header/footer tokens and downweight/remove when repeated.

**Parameterize:** allow a `header_footer_ruleset` profile:
- `scholarly_article`
- `internal_report`
- `mixed` (default)

### B. Better structure hints → better chunk boundaries
GROBID TEI often contains structure-ish cues (even if imperfect): title, abstract, section headings, references.

Use those to improve chunking in two ways:

1) **Pre-grouping before semantic chunking**
   - Instead of joining the whole document, split elements into “segments” first:
     - title/abstract/introduction/…/references
     - or “before references” vs “references”
   - Then run semantic chunking within each segment.
   - This reduces bad splits across major sections and prevents mixing body text with reference lists.

2) **Exclude or separately handle references/bibliography sections**
   - References sections are high-noise for RAG and can dominate embeddings.
   - Use TEI detection (or heuristic) to:
     - drop reference lists entirely, or
     - chunk them under a separate `chunk_type="references"` for niche use.

**Parameterize:** `include_references: true/false`, `references_handling: drop|separate|include`.

### C. Improve chunk metadata for retrieval, citation, and QA
Enriched bibliographic metadata can populate chunk fields such as:
- `document_title`
- `document_type` (article/report/book chapter)
- `doi`, `openalex_id`
- `publisher`, `venue` / `journal`
- `year`
- `authors` (or first author)
- `citation` string (generated from CSL-JSON later)

This dramatically improves:
- filtering (“only peer-reviewed articles”, “only internal reports”)
- audit (“which edition/version did this come from?”)
- downstream UI display and human review.

**Parameterize:** `chunk_metadata_fields` (which doc-level fields are copied down onto each chunk).

### D. Improve deduplication and “corpus hygiene”
Before chunking, use doc metadata to detect duplicates:
- Same DOI → likely same work (but watch versions)
- Same OpenAlex Work ID → likely same work
- Very similar title+year+first_author with different filenames → likely duplicates

Then you can:
- skip parsing/chunking duplicates, or
- keep but mark them with `qa_flags=["possible_duplicate"]`

**Parameterize:** `dedupe_policy: skip|flag|keep_all`.

### E. Fix the current “element-span mapping is conservative” limitation
This is the highest-value technical upgrade for traceability.

Right now the script joins element text → semantic chunks → loses exact element spans.

With metadata integration, you can justify investing in **element-level chunking**:
- Embed and chunk **at the element level** (or sentence level inside each element), so each chunk records:
  - exact `element_indices` list (or start/end that is true)
  - true `page_number_min/max` per chunk
  - section label (if TEI-based segmentation is used)

This makes your citations and evidence traceability much stronger—especially important for internal reports.

# 1) Scoring rubric (transparent, explainable, parameterized)

You want two things simultaneously:
- **gating** (copy/quarantine/skip)
- **classification** (scholarly vs internal report) to control OpenAlex title-search

Do this with **two parallel scores** and one combined `score_ingest`.

## 1.1 Feature extraction inputs
Features come from (in order of availability):
- prescreen (filename/path hints, cheap PDF metadata)
- GROBID TEI parse (title/authors/year/doi/sections)
- OpenAlex (DOI match always; title-search scholarly only)

## 1.2 Scores (0–1) with additive components + caps
### `score_scholarly` components (cap at 1.0)
- `+0.70` if **OpenAlex DOI match** succeeded (highest confidence)
- `+0.55` if **DOI found** (TEI or text) but OpenAlex DOI match not available
- `+0.20` if **container/journal/venue** detected (TEI or OpenAlex)
- `+0.15` if **abstract detected** (TEI)
- `+0.10` if section tokens like Methods/Results/Discussion present (TEI or headings heuristic)
- `+0.10` if references section exists and contains many citation-like entries

### `score_internal_report` components (cap at 1.0)
- `+0.50` if **report number pattern** detected (examples parameterized):
  - `EM 1110-`
  - `ERDC/`
  - `TR-`, `TM-`
  - `EP 1110-`
- `+0.35` if strong **org/distribution** tokens detected:
  - `USACE`, `ERDC`, district names, “Prepared for”, distribution statements
- `+0.20` if title contains `technical report|final report|memorandum|appendix|work plan|scope of work`
- `+0.15` if TOC/numbered sections strongly present (e.g., many headings like `1.0`, `2.0`…)

### `noise_penalty` (0–1, subtract from ingest)
- `+0.60` if OCR/text content is near-empty (very low extracted text length per page)
- `+0.20` if page count extremely low (e.g., 1-page cover sheets), unless allowlisted
- `+0.25` if file looks like a slide deck exported to PDF (heuristics: many pages, very low words/page)

### Combined gating score
- `score_ingest_raw = max(score_scholarly, score_internal_report)`
- `score_ingest = clamp(score_ingest_raw - noise_penalty, 0, 1)`

**Why this works for your environment**
- Internal reports often have no DOI and won’t be in OpenAlex; they can still score high via report patterns/org tokens.
- Scholarly works score high via DOI/OpenAlex.
- Noise gets quarantined or skipped.

## 1.3 Classification rule (for OpenAlex title-search gating)
Compute:
- if `score_scholarly >= 0.50` and `score_internal_report < 0.60` → `doc_type_guess = "scholarly"`
- else if `score_internal_report >= 0.60` → `doc_type_guess = "internal_report"`
- else → `doc_type_guess = "unknown"`

Then enforce your safer default:
- OpenAlex title-search only if `doc_type_guess == "scholarly"`.

## 1.4 “Reasons” audit string (required)
For every doc, store:
- `reasons = ["doi_found", "openalex_doi_match", "report_number:ERDC/", ...]`
- `missing_fields = ["title", "year"]` (if applicable)

This is what makes quarantine triage fast and defensible.

## 2.2 TEI-first segmentation
From GROBID TEI:
- Map TEI div/head markers to segment boundaries where possible.
- Detect bibliography:
  - TEI typically represents references in a `<listBibl>` or similar structure.
  - If present, mark that span as `references`.

Store in doc metadata:
- `tei_has_bibliography: bool`
- `tei_section_heads: [ ... ]` (normalized strings)

## 2.3 Fallback segmentation (element-heading heuristic)
If TEI structure is absent/weak:
- Identify candidate headings in unstructured elements:
  - short lines (e.g., < 120 chars)
  - Title Case / ALL CAPS / numbered section headers
- Detect “references start” boundary if a heading matches patterns:
  - `^references$`
  - `^bibliography$`
  - `^literature cited$`
  - `^works cited$`

Once references start, everything after is `segment_type="references"` unless another major boundary indicates appendices.

## 2.4 Handling appendices (optional but helpful for reports)
Heuristic:
- heading matches `^appendix\b` or `^annex\b`
- once detected, segment to `appendix`

You can choose to keep appendices in `main` or separate later; for now keep in `main` but tag them.

# 3) Element-level semantic chunking algorithm (precise spans)

Within each `segment_type` block:
1) create a list of ordered elements with non-empty text after noise removal
2) compute embeddings per element text
3) compute cosine similarity between adjacent elements
4) mark breakpoints where similarity drops below a threshold (or percentile rule matching your current `SemanticChunker` settings)
5) assemble chunks as contiguous element spans
6) enforce size bounds:
   - if too large, split at the largest internal similarity drop
   - if too small, merge with neighbor when safe

**Outputs per chunk (release blockers)**
- exact `element_index_start`, `element_index_end`
- `page_number_min/max` from contributing elements
- `segment_type`
- `chunk_corpus`:
  - `references` if segment_type == references
  - else `main`

## Tradeoffs: nested objects vs JSON-encoded strings (in JSONL)

### Option 1 — Nested objects in JSONL (recommended)
**Pros**
- No extra serialization overhead during chunk writing
- Easier to inspect and validate (real JSON types)
- Less error-prone (no “string that contains JSON” bugs)
- Lets you add fields later without breaking readers (as long as you tolerate extra keys)

**Cons**
- If you try to load JSONL directly into a rigid tabular system, nested fields require extra handling (but you already have an export stage)

### Option 2 — JSON strings in JSONL (flattened early)
**Pros**
- Easier to make a flat table later without transform
**Cons**
- Slower and uglier: you pay serialization twice and lose structure in the source-of-truth
- Harder to query/inspect (must parse JSON inside strings)
- Higher risk of inconsistent encoding

**Performance reality:** nested objects are typically *more performant overall* because you defer flattening to a single controlled step and avoid repeated encode/decode.

✅ **Decision:** nested objects in JSONL; flatten at export.

## How to structure dependencies cleanly (avoid “conda vs pip chaos”)

### Rule of thumb
- Put runtime dependencies in **`environment.yml`** (conda-forge when possible).
- Keep `pyproject.toml` minimal and focused on:
  - package name/version
  - entrypoints (console scripts)
  - *optionally* lightweight dependencies (but you can keep dependencies in conda only if you prefer).

### Two workable patterns

#### Pattern 1 (recommended for your team): “Conda owns dependencies”
- `environment.yml` lists all dependencies
- `pyproject.toml` lists **none or minimal** dependencies
- You still run `pip install -e .` so the CLI works

Pros: single dependency source of truth (conda)  
Cons: `pip install .` won’t pull deps automatically (but you’re not distributing on PyPI anyway)

#### Pattern 2: “Hybrid, packaging-native”
- `pyproject.toml` lists dependencies
- `environment.yml` installs only Python + pip + maybe heavy compiled deps
- More “standard Python packaging”

Pros: more portable outside conda  
Cons: more moving parts; can surprise users behind proxies

Given your org context and your template, **Pattern 1** is typically best.
